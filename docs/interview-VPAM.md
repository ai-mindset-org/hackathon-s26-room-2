# Спецификация MVP: Telegram-саппортер по базе знаний

## Замысел

Telegram-бот крипто-биржи автоматически отвечает клиенту с учётом его прошлой переписки и подтверждённых данных из базы знаний компании (текст + скриншоты инструкций), а при нехватке данных передаёт запрос человеку.

## Пользовательский поток

1. Клиент пишет напрямую Telegram-боту.
2. Бот определяет клиента по Telegram user ID (профиль: ID, имя, username).
3. Бот загружает историю сообщений этого пользователя с ботом.
4. Бот понимает смысл нового запроса с учётом истории.
5. Бот выполняет смысловой поиск по индексу базы знаний.
6. Модель решает, достаточно ли найденных данных для ответа без выдумок.
7. Достаточно → бот формирует персональный ответ и отправляет клиенту.
8. Недостаточно → бот сообщает клиенту об эскалации и пересылает запрос с контекстом Ефиму в личку.

## Стек и данные (зафиксировано)

- **Модель:** gpt-5.6-terra через Codex CLI по подписке ChatGPT (API-ключа нет).
- **Поиск:** локальный лексико-смысловой индекс (BM25 по чанкам md), без внешних эмбеддингов.
- **База:** локально на M1 → `/Users/agent/knowledge/BUILDIN_SELECTED_EXPORT_FINAL/`
  (та же, что на Google Drive).
  В индекс идёт **вся папка**: «База знаний» (12 разделов), «Категории вопросов»
  (12 категорий готовых ответов саппорта), «СПРАВОЧНЫЕ КАРТОЧКИ.md».
  Тематика: крипто-биржа (AML, P2P, банковские переводы, наличные, API,
  виртуальные карты, рефералка, регистрация).
- **Картинки (149 png, скриншоты инструкций):** обрабатываются vision-моделью
  на этапе индексации; извлечённая из них информация попадает в индекс и
  используется в ответах клиенту.
- **Telegram-бот:** новый, создаётся через BotFather, токен даёт Ефим, живёт в `.env`.
- **Эскалация:** личка Ефима от бота.
- **Данные о клиенте:** только Telegram-профиль + история диалога с ботом; внешних CRM нет.

## Части

### 1. Telegram и история клиента
**Цель:** принимать личные сообщения и вести историю отдельно по каждому user ID.
**Границы:** только переписка с этим ботом; внешние системы не подключаются.
**Проверка:** второе сообщение пользователя учитывает факт из первого; чужая история не подмешивается.

### 2. Индекс и смысловой поиск
**Цель:** проиндексировать всю папку базы (md + описания png), находить фрагменты по смыслу.
**Границы:** факты компании — только из индекса; веб-поиск и общие знания модели фактами не считаются.
**Проверка:** запрос «не теми словами» находит нужный фрагмент; информация со скриншота доступна в ответе.

### 3. Автоответ и передача человеку
**Цель:** автоматически закрывать подтверждённые запросы, остальные — Ефиму.
**Границы:** достаточность данных оценивает модель; при сомнении — не выдумывать.
**Проверка:** вопрос вне базы не получает выдуманных фактов, а уходит в личку Ефима с контекстом.

## Чего не делаем

- CRM, почта, WhatsApp, тикет-системы — нет.
- Анкеты, статусы аккаунтов, балансы — нет.
- Интерфейс оператора кроме лички Ефима — нет.
- Кнопка подтверждения черновиков — нет: подтверждённое бот шлёт сам.
- Секреты и клиентские данные в репозиторий — никогда.

## Критерии готовности (живой Telegram-прогон)

1. **Ответ из базы:** вопрос, покрытый базой → фактически верный ответ без добавленных сведений.
2. **Персонализация:** клиент сообщил контекст → следующий ответ его учитывает.
3. **Эскалация:** вопрос вне базы → без выдумок, клиент уведомлён, запрос с контекстом у Ефима в личке.

Дополнительно: изоляция историй пользователей; история переживает перезапуск; пустая база → эскалация; секреты только в `.env`.

## Принятые риски

- Достаточность решает модель — возможны ложный автоответ или лишняя эскалация.
- Качество ответов зависит от полноты обезличенной базы.
- Vision-описания скриншотов могут терять детали.

## Осталось неясным (решается в реализации)

- Объём истории в контексте при длинном диалоге.
