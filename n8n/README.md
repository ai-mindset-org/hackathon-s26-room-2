# n8n-пайплайн: ответ клиенту по базе + гард

Версия участника **QE2K**. Развёрнут (неактивным) на личном n8n:
`[TEST] [HACK] Ответ клиенту по базе + гард`, id `tkCI9rpfOUNoGMzF`.

```
Ручной запуск ─┐
               ├─> База знаний ─> Сделка (заглушка) ─> Черновик ─> ★ ГАРД ★ ─> прошёл?
Webhook ───────┘   (заглушка)         │                (LLM)                   ├─ да  -> отправлять
                                       └ Bitrix24 crm.deal.get (выключена)      └─ нет -> менеджеру
```

## Идея

Генерацию делает модель, а решение «увидит ли это клиент» принимает **код**.
Гард стоит жёстко в цепочке — обычной нодой, а не инструментом агента, поэтому
модель не может его обойти или «решить не вызывать». Это ровно та дыра, которая
есть в промптовых гардрейлах: они держатся на доброй воле модели.

## Что проверяет гард

**Выдумка.** Каждое число, артикул, email, ссылка и телефон черновика должны иметь
источник: буквально в базе, из запроса клиента, из сделки — или выводиться
арифметикой по прайсу. Поэтому корректное КП проходит целиком:

```
406 800  <-  расчёт: 12 × 33 900 (TS-192E)
378 324  <-  расчёт: 12 × 33 900 (TS-192E) − 7%
485 266  <-  сумма: 378 324 + 79 600 + 27 342
```

а выдуманная цена — нет.

**Регламент.** Обращение на «вы», обращение по имени, цена только с артикулом,
запрет «завтра» и безусловных обещаний («гарантирую», «100%»), обязательная
подпись, честное «в базе нет» + передача менеджеру, срок из прайса.

**Условия прайса.** Скидка 7% не применяется к позиции меньше 10 шт.

**Сверка со сделкой** (когда CRM подключена): товар вне позиций сделки, итог
расходится с суммой сделки, валюта не та, обращение не к контакту сделки,
обещание отгрузки на неподходящей стадии.

## Шов под Bitrix24

CRM сейчас — заглушка (`fixtures/deal-02.json`), но форма данных настоящая: ровно
то, что вернут `crm.deal.get` + `crm.deal.productrows.get` + `crm.contact.get`.

```json
{ "id", "currency", "total", "stage", "stage_allows_shipping",
  "contact_name", "contact_phone",
  "products": [{ "article", "name", "price", "quantity" }] }
```

Подключение Bitrix меняет **источник**, а не логику: включить выключенную
HTTP-ноду, привести ответ к этой форме — остальное работает без правок.
`deal: null` означает «CRM не подключена»: проверки по сделке молча пропускаются,
все остальные продолжают работать.

## Файлы

| Файл | Что это |
|---|---|
| `guard.js` | вся логика проверок, чистый JS без зависимостей |
| `selftest.js` | 22 теста на тех же фикстурах, что и Python-версия |
| `build-workflow.js` | вшивает свежий `guard.js` в Code-ноду, собирает `workflow.json` |
| `workflow.json` | готовый к импорту воркфлоу |
| `fixtures/deal-02.json` | заглушка сделки |

## Порядок работы

```bash
node n8n/selftest.js        # 22 из 22 должны пройти
node n8n/build-workflow.js  # пересобрать workflow.json
```

Логика живёт только в `guard.js`. В JSON она попадает сборкой, а не копипастой —
поэтому воркфлоу и тесты не расходятся.

## Почему JS, а не Python

Python-версия (`src/guard/`) осталась как эталон и спецификация. В n8n логика
переписана на JS сознательно: Python в Code-ноде работает через Pyodide, у
которого критическая уязвимость обхода песочницы (GHSA-62r4-hw23-cc8v, CVSS 9.9),
и в n8n 2.0 он вообще убран. JS-нода не требует ни деплоя, ни отдельного сервиса.

Грабли при переносе, если будете править регулярки: **в JS `\w` и `\b` не знают
кириллицы** (`\w` === `[A-Za-z0-9_]`). Поэтому `скидк\w*` молча никогда не
сработает — в коде вместо этого `RW = [а-яёА-ЯЁ]` и явные границы слова.
